## 为什么做

Je = **Just Enough**。名字就是这个项目的全部主张：给够就好，不多给。

我拿它读全英文的学术论文。用下来发现单步 RAG 有三个结构性缺陷，而且都不是调参能解决的：

| 单步 RAG 的问题 | 做法 |
| --- | --- |
| 简单题和难题走同一条链 | 动态路由 + 迭代循环，简单题首轮即停 |
| 闲聊也过检索 | 意图判断分发，闲聊零检索 |
| 固定 top-k，不够也硬答 | 充分性判断 + 缺口识别，信息不够自动追问 |

第二条尤其重要。闲聊被强行检索出几段论文，模型就会煞有介事地引用它们——
这是幻觉里最难发现的一种，因为引用看起来是真的。

## 关键决策

### 检索轮数和终止时机交给模型判断，不用固定链

单步 RAG 的核心毛病是「简单题和难题走同一条链」。我改成由模型在运行时根据中间结果
自己决定是否继续检索、何时停止回答——检索轮数、查询内容、终止时机都是动态的。

代价直接体现在账单上：每次决策本身就是一次 LLM 调用，简单题也要付一次判断成本。
更贵的是复合题——每个子需求都走完整迭代循环，比免检直答多付约 3 次调用（筛选 + 抽取 + 判断）。
我认这个代价，换的是漏检风险消失。

### 表格、图片、公式用 VLM 生成 caption，单独成 chunk

论文里最难召回的不是正文，是多栏排版、表格、矢量图和公式——它们要么被解析器丢掉，
要么被切成语义破碎的片段。我的做法是用 Docling 做结构化提取，
再让 VLM 给这些内容生成 caption，**分别构造特殊 chunk** 参与检索。

代价是入库链路变重：解析要跑 Docling，表格摘要要调 VLM，入库时间和费用都上去了。
所以增量入库按 SHA256 跳过未修改的文件，重复摄取几乎零成本。

### 预算同时设硬上限和软停

`max_rounds` 是硬上限，超了强制总结；`max_llm_calls` / `max_tokens` / `max_elapsed_s`
是软停——当前轮跑完就不再开新轮。复合题的子需求之间还要全局核算，不能各自为政。

代价是软停会让单次回答的实际开销略微超出预算：它保证的是「不会无限跑」，
不是「绝不超过这个数」。我更怕的是答到一半被硬砍。

### 解析与检索层复用 RAG-MCP，两个项目各自演进

JeRAG 的解析和检索能力来自 RAG-MCP，只提取可复用的部分，在其上重写为 Agentic RAG。
两个项目的开发目的不同：一个面向「给 Agent 提供检索工具」，一个面向「把问题答对」。

代价是同一份解析与检索逻辑要在两个仓库之间同步，改一处要想另一处。

## 结果

- 三个阶段：会话式问答底座、agentic 化（迭代循环 / 路由 / 任务分解 + 并行 + 聚合）**已完成**；
  联网源扩展未开始
- 检索链路四段：chroma + BM25 混合检索 → RRF 融合 → references 段过滤 →
  cross-encoder（`bge-reranker-v2-m3`）重排
- 全流程 trace 落 jsonl，可离线出行为指标：轮数分布、每轮查询不重复率、预算命中
- 151 个 Python 文件、32 个测试文件，覆盖检索、循环、分解、并行、路由

## 不足与下一步

1. **语料只支持英文。** 题集、分词、词干都按英文口径做，非英文提问的召回质量有限。
2. **直接回答分支零证据零引用。** 知识题如果被误判进这条分支，会产生不可发现的幻觉。
   目前靠路由探针量化跟踪误判率，但没有根治。
3. **联网调研还没做。** 库外知识和时效性问题答不了，暂时靠轮数与预算上限兜底。
   下一步是在迭代循环的工具池里加 web（搜索 + 抓取 + 阅读），并给充分性判断补上第三态：
   「本源不可能答出来 → 换源」。
