## 背景

「读记」需要一个"写完就能搜"的搜索。数据量很小（一万多条笔记），
所以我不想引入 Elasticsearch 或者 Meilisearch 这类独立服务——
一个桌面应用带一个搜索服务，听起来就很荒唐。

SQLite 自带的 FTS5 扩展是天然选择。但中文搜索有个绕不过去的问题：
**FTS5 默认的分词器不认识中文。**

## 第一个坑：默认分词器把整句话当成一个词

FTS5 的 `unicode61` 分词器按空格和标点切词，对英文很好用。
中文没有空格，所以"读书笔记"会被当成一个完整的词元。

结果是：搜"笔记"搜不到任何东西。

## 三个可选方案

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 自己预分词（jieba 等） | 效果最好 | 要维护词库，索引和查询都要走同一套逻辑 |
| `trigram` 分词器 | 内置，零依赖 | 索引体积大，短词召回差 |
| 一个字一个词元 | 召回率最高 | 索引爆炸，几乎不可用 |

我先试了 trigram，因为它是内置的，一行就能开：

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(
  content,
  tokenize = 'trigram'
);
```

## 第二个坑：短查询过召回

trigram 的原理是把文本切成连续三个字符的片段。所以"读书笔记"会被切成
`读书笔`、`书笔记` 这几个片段。

问题来了：搜"读记"（两个字符）时，trigram 没法匹配——因为查询串本身不足三个字符。
而搜"笔记"能命中，但也会把"笔记本""笔记软件"这些无关内容一起带出来。

我的处理办法是**混合策略**：

- 查询串长度 ≥ 3：走 FTS5，用 `rank` 排序
- 查询串长度 < 3：回退到 `LIKE '%词%'` 全表扫描

一万多条数据下，`LIKE` 全表扫描大约 30–60 毫秒，用户感知不到。
这个取舍很划算：**用一点性能换掉一整套分词依赖。**

```js
const useFts = query.trim().length >= 3;
const sql = useFts
  ? `SELECT id FROM notes_fts WHERE notes_fts MATCH ? ORDER BY rank LIMIT 50`
  : `SELECT id FROM notes WHERE content LIKE ? LIMIT 50`;
```

## 第三个坑：索引体积

trigram 的索引大约是正文的 2.6 倍。我一开始有点慌，实测之后发现可以接受：

- 12,000 条摘抄，正文约 1.4MB
- 索引约 3.7MB

对一个桌面应用来说，这完全可以忽略。但如果你的数据是 100MB 级别的长文，
这个倍数就要重新考虑了。

## 高亮怎么做

FTS5 提供了 `snippet()` 函数，可以直接在 SQL 层出高亮片段：

```sql
SELECT snippet(notes_fts, 0, '<mark>', '</mark>', '…', 12)
FROM notes_fts WHERE notes_fts MATCH ?
```

注意两点：返回的是带 HTML 标签的字符串，**渲染前一定要转义原文**，
否则就是自己给自己开了个 XSS 后门；另外片段长度要按界面宽度调，
我用的 12 个词元在侧栏里刚好两行。

## 如果重来一次

我大概还是会选 trigram，但会早点做那件事：**在真实数据上测召回率，而不是用测试数据。**

我最初的测试用的是十几条规整的笔记，效果很好。换成真实的 12,000 条之后，
才发现短查询的问题——真实数据里的口语化表达、错别字、混合中英文，
都不是测试数据能覆盖的。
